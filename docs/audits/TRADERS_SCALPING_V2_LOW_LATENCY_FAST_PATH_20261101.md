# Scalping v2: отчёт о сокращении задержки анализа

Дата проверки: 2026-11-01 (UTC). Ветка: `feature/engine-platform`.

## Итог

Статус: **PASS для контура «закрытие свечи → завершение анализа 20 символов»**.

На естественной 5-минутной границе `2026-11-01 03:15:00 UTC` все 20 символов были обработаны за **7,821 с** от момента закрытия свечи. Это укладывается в принятый бюджет: целевой p95 не более 8 секунд, жёсткий предел 10 секунд.

Проверка не создавала искусственных сигналов, планов, команд, ордеров или позиций. Поэтому задержка **«готовый торговый сигнал → PAPER-команда → открытая позиция» остаётся UNPROVEN** до первого естественного сигнала новой сессии.

## Реализованные изменения

1. Добавлен WebSocket fast path Binance для закрытых свечей (`x=true`) с сохранением 1m/5m/15m/1h; REST-синхронизация сохранена как восстановительный контур.
2. Убрана фиксированная 15-секундная задержка свежести для 1m и 5m; для старших таймфреймов защитные задержки сохранены.
3. Poll/retry оркестратора сокращён с 10/5 секунд до 0,5/0,5 секунды.
4. Детектор закрытых окон загружает последние свечи всей вселенной пакетно и с ограниченным временным диапазоном.
5. Проверка freshness для 20 символов выполняется одним чтением состояния вместо серии отдельных запросов.
6. Все 20 символов анализируются параллельно.
7. Независимые `mark_running`/`finish` используют отдельные транзакции; общий lock оставлен только для внутрипроцессных итоговых счётчиков.
8. Health-метрики больше не материализуют 244 871 исторический запуск Scalping v2 каждые несколько секунд: подсчёты перенесены в SQL-агрегаты.
9. Safety counters также агрегируются в базе вместо загрузки всей истории результатов при старте.
10. Добавлены явный пул соединений оркестратора и runtime source identity; Docker-образ пересобран и развёрнут без рестарта PostgreSQL и operator API.

## Обнаруженная первопричина 49–76 секунд

Задержка была составной:

- программное ожидание REST freshness 15 секунд;
- фактическое получение свечей через REST через 17–21 секунду;
- polling оркестратора раз в 10 секунд;
- последовательные служебные чтения freshness;
- очередь символов;
- критический дефект observability: регулярная загрузка сотен тысяч исторических ORM-объектов для health-метрик.

Последний пункт объяснял нестабильные всплески CPU/PostgreSQL и памяти до нескольких гигабайт. После SQL-агрегации холодный старт возвращается примерно к 77 МБ и не выполняет полный проход по истории.

## Что ещё требуется доказать

1. Дождаться естественного сигнала и измерить отдельно:
   - завершение анализа → создание плана;
   - план → selector;
   - selector → PAPER command;
   - command → simulated fill;
   - fill → позиция OPEN.
2. Набрать минимум 24–48 часов естественных границ и рассчитать p50/p95/p99, а не делать вывод по одной контрольной свече.
3. Добавить постоянный latency SLO alarm: warning при >8 с и fail-closed для новой команды при >10 с.
4. Не считать достигнутую скорость доказательством прибыльности. Win Rate >50%, PF ≥1,20 и положительный net PnL требуют отдельной natural PAPER выборки.

## Safety verdict

Торговые формулы, веса, стопы, цели, комиссии, риск и стартовый капитал 1000 USDT в этой работе не менялись. Миграции, deploy LIVE, реальные ордера и мутации исторических PAPER-данных не выполнялись. Пользовательские удаления отчётов и прочий исходный dirty state не включены в commits этой работы.
